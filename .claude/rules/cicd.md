# CI/CD

How a change reaches `master` and the live site (2026-10-11). The road to `master` is ../backseat-driver's (its `.claude/rules/cicd.md`); the deploys follow merecatholicity.com's principles: the merge is the deploy, CI is the build of record, no secret on a pull request, every deploy checks itself.

## The road to master

- `master` takes no direct push: the ruleset (`terraform/github.tf`) wants a pull request, `check` and Terraform's `plan` green (from GitHub Actions, app 15368, so a status of that name from anywhere else satisfies nothing), and one approval; a push dismisses a stale approval. No force push, no deletion. Not strict: a pull request need not be on the newest `master` (the merge's own check runs again before it deploys). No bypass actor: the owner, their agents and everyone else get the same rule.
- Auto-merge for the owner and the Claude sessions the owner drives, nobody else. `owner-merge.yml` (`pull_request_target`) approves a pull request whose author and event sender are user id 26800291 (a-schaefers), from this repository, not a draft, at the head it was woken for, then arms auto-merge if nobody has. Anyone else's (other people, other Claudes, Dependabot, forks) waits for the owner's approval by hand; so does the owner's own after someone else pushes to it, until the owner pushes again. A draft holds one back.
- `owner-merge.yml` must never run the pull request's code: no checkout, no `uses:`, nothing from the event in a shell but the number, the head hash, the repository and the token. `scripts/test_workflows.py` (in `make check`) holds it to that.
- Who arms auto-merge decides whether the merge deploys at once: a merge armed with the workflow's token is GitHub Actions' push, which starts no workflow. `scripts/ship.sh` arms it as the owner, so the merge is the owner's and `deploy.yml` runs on it; when `owner-merge.yml` armed it (or merged it), that job waits for the merge and dispatches `deploy.yml`, the one run its token may start, so every merge deploys at once (owner, 2026-10-12); the hourly run is the safety net.

## Shipping

- Commit on a branch (or in a worktree), then `scripts/ship.sh`: pushes `HEAD` to the branch (a detached `HEAD` ships as `agent/<worktree>`), opens the pull request or finds the open one, arms auto-merge as you with `--match-head-commit`, waits for the merge or names the failing check. It refuses to ship from `master` and acts only on this repository's own pull request at the commit it pushed. `--draft` opens one that waits. A red check leaves auto-merge armed: fix, commit, run it again.
- Other sessions ship too: merge `origin/master` into your branch when it conflicts, stage by path, never `git add -A`.

## Workflows

- `check.yml`, the required check: `make check` (the site built from `content/`, `src/` and `static/` into `build/`, then `public/`: `scripts/build.ts` (esbuild, Tailwind) then Emacs, then `scripts/dist.sh`; `scripts/check-dist.ts` over `public/`, every TypeScript project type-checked, the Workers' tests, `scripts/test_workflows.py`) in a Debian 13 container (Emacs 30.1, Org 9.7.11, pinned by digest; Node 24). It runs on every pull request with no secret and no path filter (a required check that never reports holds a pull request at "Expected" for ever; never rename the job without the ruleset). It runs `make check` in two halves: `make build check-dist typecheck`, then the upload of `public/` as the artifact `site`, then `make test`, so the plugin code the license tests import from backseat-driver's `main` runs only after the site that deploys is sealed.
- `deploy.yml`, on every push to `master` (and hourly, and by hand): `check.yml` again on the merged commit, then in the `production` environment: the Workers' admin pages compiled (`make workers`, before any step holds the token), the site Worker deployed with that artifact (`wrangler deploy --tag <commit>`: the changed files upload and the version switches at once), the license server and the contact form through `scripts/deploy-worker.sh` (only when their folder or `package-lock.json` changed since their live version's tag), then `scripts/smoke.sh` against the live site, every request to the site with a nonce (`?probe=<commit>-<attempt>-<random>`, an address no cache has seen; never a hashed file by its name) (this build's pages and `version.json`, revalidated; a 404 for nothing; `/admin` closed; a video's Range answered 206; the license server's answers no-store and never a cache HIT). Deploys never overlap and are never cancelled. The hourly run first asks whether the site's live version is `master`'s, and stops there when it is.
- `owner-merge.yml`: above.
- `terraform.yml` (2026-10-12, as ../merecatholicity.com's and ../enchant.games'): `terraform/` is the repositories' GitHub settings and the zone's Cloudflare configuration (`terraform/README.md`). Every pull request: `fmt` and an offline `validate`, no credentials (every secret blanked on a `pull_request` event in its own expression). A merge that changes `terraform/` (or a run by hand): `plan` with the repository secrets `CLOUDFLARE_ROOT_TOKEN` and `GH_ROOT_TOKEN`, the state in R2 (`adamschaefers-tfstate`, its S3 pair derived from the Cloudflare token), and when it has changes, `apply` waits on the `terraform-production` environment for the owner's review (the browser, or `scripts/ci_approve.sh`), re-plans, and refuses a plan other than the one reviewed. It never prints a plan or uploads the plan file (this repository's logs are public; state holds secrets): reviewers see `scripts/tf_plan_summary.py`. A destroy or replace fails the plan unless dispatched with `allow_destroy`.
- `purge-cache.yml`, by hand only: empties Cloudflare's cache of media.adamschaefers.com (or, ticked, the whole zone) with `CLOUDFLARE_PURGE_TOKEN`; it checks nothing out and runs no code from the repository.
- `signing-key.yml`, by hand only (2026-10-13): the license signing key's backup, the `production` secret `SIGNING_KEY` (Credentials). It checks that the backup's public half is live-1's and that the license server signs with live-1 (the first of its `/v1/public-keys`); ticked `restore`, it puts the backup back into the Worker through Cloudflare's API between the two, and never when the first check fails. No checkout, no code from the repository, nothing printed but public halves; a test holds it to that and to the kid in `license-worker/wrangler.jsonc`.
- Every `uses:` names a commit with a `# vX.Y.Z` comment; `.github/dependabot.yml` bumps the action pins and the npm packages (`package.json`: wrangler, TypeScript, esbuild, Tailwind, lit-html, the fonts, the types) weekly, each pull request waiting for the owner's approval (a merged bump redeploys the site, and every Worker when the lockfile changes). The Debian image digest in `check.yml` moves by hand.

## Cache busting

As in ../merecatholicity.com (2026-10-11), fitted to Workers Static Assets. Versions: the script, styles and fonts are named by their content's sha1 (`site.el`, `js/app.<hash>.js`), kept for good (`_headers`), and `scripts/check-dist.ts` fails on a name that isn't its file's hash; everything else revalidates on every request (ETag, 304). `version.json` (`scripts/dist.sh`: `{build, assets: {app.js, site.css}}`, checked against every page) is what `src/version.ts` fetches no-store, on returning to the tab and hourly, to compare with the names the open page loaded, offering Reload, never reloading by itself or over a half-written form (`scripts/version.test.ts`). Purge: the site's files are each deploy's own and no zone purge reaches them (a purged page answered HIT, 2026-10-11), so the deploy purges nothing; the zone cache holds the media domain, which the admin purges per file on Replace and Delete (`PURGE_TOKEN`) and `purge-cache.yml` purges whole. The zone's Browser Cache TTL respects the origin.

## Credentials

- One: `CLOUDFLARE_API_TOKEN`, a GitHub secret in the `production` environment, which only `master` may deploy from, so no pull request (and no workflow but `deploy.yml` and the `signing-key.yml` button, which a test holds to) can read it. An account-owned token, `adamschaefers.com CI`: Workers Scripts edit on `adamschaefers-site`, `adamschaefers-licenses` and `adamschaefers-contact` only, and Workers Routes edit on the adamschaefers.com zone. It can't touch R2, D1, DNS, Access or any other Worker. `CLOUDFLARE_ACCOUNT_ID` is a repository variable (an id, not a secret). Rotate: mint a new token with the same policy (dashboard, Manage Account, Account API Tokens), `gh secret set CLOUDFLARE_API_TOKEN --env production`, dispatch `deploy.yml`, delete the old token.
- `CLOUDFLARE_PURGE_TOKEN` (production environment, `purge-cache.yml` only) and the site Worker's secret `PURGE_TOKEN` (the admin's per-file purge): the account-wide Cloudflare token ../merecatholicity.com's pipeline uses (`CLOUDFLARE_ROOT_TOKEN` in `~/.config/merecatholicity/ci.env`); a hobby account, one broad token for purging. Rotating it there means setting all three copies here too (`gh secret set CLOUDFLARE_PURGE_TOKEN --env production`; `npx wrangler secret put PURGE_TOKEN -c site-worker/wrangler.jsonc`; `gh secret set CLOUDFLARE_ROOT_TOKEN`, below).
- Terraform's two (2026-10-12), repository secrets because the plan runs before any gate, read only by `terraform.yml` and blanked there on every `pull_request` event (a test holds to both): `CLOUDFLARE_ROOT_TOKEN`, the same account token, and `GH_ROOT_TOKEN`, a classic token with no expiry the owner minted for this pipeline and ../enchant.games' (its copy is `~/.config/hobby/github-token`; ../merecatholicity.com keeps its own). Rotate: the new value into that file, then `gh secret set GH_ROOT_TOKEN < ~/.config/hobby/github-token` in both repositories.
- The Workers' own secrets (Stripe, Resend, signing keys, Turnstile) are Worker secrets, set by hand with `wrangler secret put`, never in git; a deploy leaves them as they are. Cloudflare never shows one again, and no copy is kept (2026-10-13, as in ../merecatholicity.com and ../enchant.games): a lost or leaked one is made again at its source, put back with `wrangler secret put`, and the old one revoked. The license server's `STRIPE_SECRET_KEY`: Stripe, API keys, a restricted key with Checkout Sessions write (the Worker only creates and reads Checkout Sessions), then the standard key rolled so no old value works; `STRIPE_WEBHOOK_SECRET`: the signing secret of the `/v1/stripe/webhook` endpoint, which Stripe reveals any time (Roll secret makes a new one); `RESEND_API_KEY`: a new send-only key, then the old one deleted; each Worker's `TURNSTILE_SECRET`: its widget's secret, which Cloudflare shows any time (`npx wrangler turnstile widget get <sitekey>`) and rotates on request; `PURGE_TOKEN`: above. The exception is a product's signing key (`SIGNING_KEY`, `SIGNING_KEY_<PRODUCT>`): its public half ships inside the product's app, so replacing it takes a release of the app, and copies older than that release can't check the keys it signs. So each one is backed up as the GitHub secret of the same name in the `production` environment (the owner's choice, 2026-10-13), set by hand (Settings, Environments, production), which nobody can read back and only `signing-key.yml` names (a test holds it): that widens nothing, since whatever can deploy the license server could already read its secrets. Never a repository or a chat. Rotating one: `license-worker/wrangler.jsonc`; the new key's backup and public half go into the secret and `signing-key.yml`.

## Settings

- Terraform (`terraform/`, its README) since 2026-10-12, when it adopted what `scripts/github-settings.sh` held and what was done by hand on Cloudflare: the ruleset; the workflow token read only and allowed to approve pull requests; auto-merge, merge commits, delete branch on merge, update branch; only GitHub-owned and verified actions, each pinned to a commit; secret scanning with push protection; Dependabot alerts and security fixes; the `production` environment and the `terraform-production` gate (master only, the owner's review, no admin bypass); the account and zone id variables; and on Cloudflare the zone and its settings (Browser Cache TTL respecting the origin, Smart Tiered Cache), every DNS record (the apex placeholder `AAAA 100::` among them), the license store's rate limit, bot management, both Turnstile widgets, the license database, the `adamschaefers-media` bucket (r2.dev off), both Access applications, and the state bucket. Two settings the provider can't hold stay set by hand (`terraform/README.md`): a fork's workflows waiting for approval every time, and GitHub Pages staying off.
- The three sites' Terraform never share a resource: this one owns adamschaefers.com's zone, repositories and objects (nothing of one site serves another: since 2026-10-12 ../enchant.games' Press page has its own contact Worker and widget); ../merecatholicity.com's and ../enchant.games' own theirs; the account, its tokens, its Email Routing destination and its Zero Trust organization are nobody's. So an apply in one never shows as drift in another.
- Actions may approve pull requests only because the owner is the one collaborator: anyone else with write access could approve their own pull request through a workflow on their branch. Revisit before granting anyone write access.
- The emergency door: when `check` itself is broken and its fix cannot pass it, the owner sets the ruleset's enforcement to `"disabled"` (Settings, Rules; the next plan shows it as drift until it is set back, or set it in `terraform/github.tf` and apply), merges the fix, and sets it back. Never a bypass actor. A deploy by hand from a laptop (`npx wrangler deploy -c <worker>/wrangler.jsonc` after `make build`) is for when CI itself is down; the next merge's deploy replaces it.

## Done by hand, on purpose

- Cloudflare: the media bucket's custom domain binding (media.adamschaefers.com; the provider can't import it, its DNS record is Terraform's), the Access applications' policy ("Adam only", the older app-scoped kind the provider can't import), and D1 migrations (CLAUDE.md). None changes with a merge.
- The tokens: the scoped Cloudflare CI token deploy.yml uses (`CLOUDFLARE_API_TOKEN`) and the purge token (`CLOUDFLARE_PURGE_TOKEN`), environment secrets in `production`, minted in the dashboard; and Terraform's two repository secrets, `CLOUDFLARE_ROOT_TOKEN` (the account token the three sites share, `~/.config/merecatholicity/ci.env`) and `GH_ROOT_TOKEN` (a classic token the owner minted on 2026-10-12 for this pipeline and ../enchant.games', `~/.config/hobby/github-token`). None is managed by Terraform; a lost one is replaced (`terraform/README.md`).
